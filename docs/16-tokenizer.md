# 16 — Tokenizer

Settles **D5** of [13](13-open-decisions.md). Facts extracted from the model's
`tokenizer.json`, not from assumption.

## What it is

BPE in the **GPT-4 / tiktoken** scheme, wrapped in HuggingFace `tokenizers`
format:

```
model.type                  BPE
model.vocab                 154,820 entries
model.merges                321,649 rules
model.byte_fallback         false
model.ignore_merges         true
model.unk_token             null
normalizer                  null
pre_tokenizer               Sequence[ Split(regex, Isolated), ByteLevel ]
decoder / post_processor    ByteLevel
added_tokens                36 special (154820..154855)
vocab_size (config)         154,880   <- there is slack at the end
```

No normaliser and no `unk`: every input byte is representable.

## The four stages

### 1. Regex pre-tokenisation

```
(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}{1,3}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+
```

It is the `cl100k_base` pattern. It requires the Unicode classes `\p{L}` and
`\p{N}`, a case-insensitive group and negative lookahead.

**Do not implement a regex engine.** The correct alternative is a hand-written
state machine for *this* pattern, with generated Unicode tables — which is
exactly what the streaming engine does in `tok_unicode.h` and
`tok_unicode_o200k.h`, generated by its `gen_unicode.py`. Reusing the approach
(and possibly the generator) saves the most tedious part, the one most prone to
subtle error.

What the tables need to answer, per code point: *is it a letter?* (`\p{L}`), *is
it a number?* (`\p{N}`), *is it whitespace?* (`\s`). Compressed ranges, binary
search.

An error here does not blow up: it produces a slightly different split, different
ids and different output from the oracle — with a perfectly correct forward. It
is the kind of bug that eats days if the test does not isolate the tokenizer.

### 2. ByteLevel

Each byte `0..255` becomes a code point through GPT-2's table: printables map to
themselves, the rest to `0x100 + n`. It is how a space becomes `Ġ` in the
vocabulary.

A fixed 256-entry table, generated once. `add_prefix_space=false` — do **not**
insert a leading space.

### 3. BPE with `ignore_merges = true`

This flag changes the algorithm and is easy to miss:

> If the pre-token's string is in the vocabulary **in full**, use that id
> directly and **apply no merges at all**.

Only when it is not does the classic BPE run: adjacent pairs, repeatedly applying
the lowest-ranked one.

Ignoring the flag produces different tokenisation for precisely the most common
words — the ones that are in the vocabulary whole.

### 4. Special tokens

36 entries in `added_tokens`, ids 154820..154855: `<|endoftext|>`, `[MASK]`,
`[gMASK]`, `[sMASK]`, `<sop>`, `<eop>`, `<|system|>`, `<|user|>`, and the rest.

They are recognised **before** the regex, by exact match, and never go through
BPE. The chat template emits them; an agentic CLI depends on them to delimit
turns and tool calls.

`vocab_size` is 154,880 against 154,856 ids in use: the slack is `lm_head`
padding. Ids in that range must never be sampled — the sampling mask has to know
that.

## C structures

| structure | contents | size |
|---|---|---|
| `vocab` | id → bytes | ~2 MB |
| `lookup` | bytes → id, open hashing | ~2 MB |
| `merges` | (id, id) → rank, open hashing | ~5 MB, 321,649 entries |
| `unicode` | ranges of `\p{L}`, `\p{N}`, `\s` | ~20 KB |
| `byte_map` | 256 entries, both directions | trivial |

All precompiled and persisted as per [12](12-persistent-state.md): parsing
321,649 merges from JSON on every open is pure waste. Load = `mmap`.

The merge lookup is encode's hot loop. Open hashing with a 64-bit key
`(left_id << 32) | right_id`; the streaming engine learned the hard way that a
linear scan here costs *"decine di secondi"*.

## Testing

Without this there is no way to trust it:

1. **Round-trip**: `decode(encode(s)) == s` for a test corpus with CJK, emoji,
   runs of spaces, line breaks and bytes that are invalid UTF-8.
2. **Equality against the reference**: the same ids as HF's `tokenizers` for the
   same corpus. That is the test that matters, and it is cheap — generate the
   expected ids once in Python and compare in C.
3. **Special tokens**: each of the 36 comes back with the right id, and is not
   split.
4. **Vocabulary boundary**: ids 154856..154879 are never generated.

Test 2 has to run **before** the first forward test. A wrong tokenizer makes M1's
oracle fail with a perfectly correct engine, and the debugging starts in the
wrong place.
