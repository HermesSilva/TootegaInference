1 Recepção — o socket e o JSON

O motor sobe em modo serve (src/server.c), escuta TCP (Transmission Control Protocol) na porta e fala o protocolo compatível com a API (Application Programming Interface) de chat. Um POST chega, o corpo é lido e o parser JSON (JavaScript Object Notation) próprio (src/json.c, zero dependências) o transforma em árvore.

// o que o cliente envia
{
  "messages": [
    { "role": "user", "content": "O que é a Arena na Cosmologia Composicional?" }
  ],
  "temperature": 0.8, "top_p": 0.95, "top_k": 40
}

2 Prompt & template de chat

O motor reconstrói os ids do zero a cada pedido e monta o prefixo da conversa, byte a byte como o chat_template.jinja do modelo. Os marcadores de papel (<|user|>, <|assistant|>) delimitam os turnos.

Por que reconstruir tudo? O casamento de prefixo (tt_state_match_prefix) decide o que reaproveitar do cache. Reconstruir garante que uma conversa reproduzida no turno 3 gere exatamente os mesmos ids do turno 1 — condição para o KV cache sobreviver à rodada (server.c).

3 Retrieval BM25 — buscar o trecho certo

A busca usa o BM25 (Best Matching 25, a função de ranqueamento clássica de recuperação de texto). O modelo foi treinado com RAFT (Retrieval-Augmented Fine-Tuning, ajuste fino com recuperação aumentada): lê, não decora. Sem o trecho no contexto, ele erra a doutrina (0 de 11 respostas corretas sem trecho; 26 de 29 com trecho, docs/22). Por isso a recuperação é requisito, não acessório — e roda no próprio motor (src/retrieve.c), não num serviço externo.

O trecho entra no último turno do usuário e é reproduzido no replay, não só na última mensagem: reescrever apenas a última mudaria o prefixo a cada envio e forçaria re-prefill da conversa inteira. Se a pergunta não compartilha termo algum com o corpus, nada é recuperado — e o prompt segue limpo.

4 Tokenização — texto vira ids

O tokenizador próprio (src/tokenizer.c + unicode_tables.h gerado por tools/ucd) parte o texto em subpalavras e devolve inteiros. Cada id é um índice no vocabulário de 154 880 entradas.

5 Prefill — preencher o cache KV

Antes de gerar, o motor passa todos os ids do prompt pelo modelo para popular o cache de chave/valor (KV) das 47 camadas. É a fase mais cara — e, sob RAFT, a que domina o tempo, porque os trechos recuperados mudam por pergunta e o cache de prefixo não ajuda.

6 Uma camada por dentro (tt_forward)

Cada uma das 47 camadas repete a mesma estrutura: normaliza, atende (MLA), soma o residual, normaliza de novo e passa pela MLP (Multi-Layer Perceptron, a rede densa de retropropagação) — densa na 1ª camada, MoE (Mixture of Experts, mistura de especialistas) nas outras 46 (first_k_dense_replace = 1).

7 Atenção MLA — olhar o passado, comprimido

A atenção latente multi-cabeça (MLA) projeta query e chave/valor por um posto baixo, via LoRA (Low-Rank Adaptation, adaptação de posto baixo) na query, e aplica RoPE (Rotary Position Embedding, codificação rotativa de posição) nas dimensões rotativas. Em vez de expandir cada posição do cache, projeta-se a query uma vez para o espaço comprimido — custo fixo, independente do comprimento do contexto (docs/13, D11).

8 MoE — escolher 4 experts entre 64

Nas 46 camadas MoE, um roteador pontua os 64 experts para o token atual e escolhe os 4 melhores. Só esses 4 (mais 1 expert compartilhado, sempre ativo) processam o token — é o que mantém ~1,1 GB ativos por token num modelo de 31 B.

9 Amostragem — dos logits a um token

Depois da última camada, uma projeção final dá um logit por entrada do vocabulário (154 880 valores). O amostrador (src/sample.c) escolhe o próximo id.

10 Decode, detokenização e streaming

O id escolhido vira texto pelo caminho inverso da fase 4 e é enviado ao cliente na hora. Então ele realimenta o forward como próximo token de entrada — o laço se repete até sair um token de parada (<EOS>, End Of Sequence, fim de sequência) ou atingir o limite n_max.

Números medidos (EPYC 9535, container int4, ~1,1k tokens de contexto): prefill ~70 s, decode 10–14 tok/s, 16,8 GB residentes. O prefill domina, e é estrutural para RAFT — os trechos recuperados mudam por pergunta, então o cache de prefixo do chat não ajuda.

+ Nota: a camada MTP — Multi-Token Prediction (especulação)

O checkpoint carrega uma cabeça de MTP (multi-token prediction, predição de múltiplos tokens) (mtp_layer = 47, num_nextn_predict_layers = 1). É o caminho para adivinhar o próximo token adiante e acelerar o decode — preservado byte-a-byte no container, mesmo quando não está no caminho ativo.
